## 2. `inDistrict()` で落ちた件は記録されるか → **どこにも残らない**

**これは本物。**発端が空振りでも、この構造自体は事実として残る。

```js
// district-sweep.js:1709-1710
b.inDistrict   = b.addresses.some(a => inDistrict(a, district));
b.addressKnown = b.addresses.length > 0;

// district-sweep.js:1721
const here = merged.filter(b => b.inDistrict);   // ← ここで捨てる
```

`classify()` は `here` しか見ない。**落選したバケットは `results` に入らないので、
`MISSING` にも `ORPHAN` にも `IN_DATA` にも出ない。**
md 生成側（`renderEntry` 以下）にも、落選分を出す節は**存在しない**。
標準出力へのログも無い。

**`b.addressKnown` は 1710 で代入されるだけで、ファイル中の出現回数は1回。
どこからも読まれていない。**
「住所が無くて落ちた」と「地区外だから落ちた」を区別できる材料が**すでに計算されているのに、
使われないまま捨てられている。**

### 唯一の痕跡と、それが信号にならない理由

ソース表の「うちこの地区」列（1991行）だけが手がかりになる。

```js
const here = c.items.filter(i => i.address && inDistrict(i.address, ctx.district)).length;
```

**ただしこれは3つの原因を1つの数字に混ぜている。**

| | 原因 | 正常か |
|---|---|---|
| (a) | **市単位のソース vs 大字単位の地区。**じゃらんは市全体を取るが、地区は「北杜市高根町清里」のような大字単位 | **正常。支配的** |
| (b) | **住所を持たないソース。**なっぷ・ウォーカープラス（市区町村まで）は `i.address` が無く、常に「この地区0」に落ちる | 既知の限界 |
| (c) | **ソース側の住所が誤っている** | 今回は**確認できず** |

**実測で (a) が圧倒的**（1067 → 139）。**したがってこの列の落差を「汚染の疑い」の指標には使えない。**
数字は出ているが、**数字が出ていること自体は、その数字が何かを意味することの証拠にならない**（§18-3 追記）。

**(b) の実例**（`sweep-都留市.md` のソース表）:

| ソース | 取得 | うちこの地区 |
|---|---|---|
| なっぷ yamanashi/otsuki_turushi | **20** | **0** |
| ウォーカープラス 山梨県 | 10 | 1 |

**なっぷの20件は、名前しか無いので1件も地区判定に乗らない。**
他の住所付きソースと名寄せで合流できた分だけが生き残り、**合流できなかった分は黙って消える。**
`sweep-都留市.md` の「限界」節は
「**そのソースにしか無い施設は、この検査から漏れる**」と**文章では書いてあるが、
何件がどう漏れたかは一度も列挙されていない。**

### 名寄せ経由で「引きずられる」経路も構造上ありうる

`mergeItems` はバケット単位で住所を持つ（1667行）。
**住所を持たないソースの項目が、誤った住所を持つ項目と名前で同じバケットに入ると、
バケットごと地区外に落ちる。**
`b.inDistrict` は `some()` なので**正しい住所が1つでもあれば救われる**が、
**誤住所しか無いバケットは救われない。**
——今回は (c) が確認できなかったので、**この経路が実際に発火した例はまだ1件も無い。**
