## 2. 新設したフィールドと意味の使い分け

すべて `lib/types.ts` に定義とコメントがある。ここでは**使い分けの理由**を書く。

### 2-1. `status` — 掲載状態（既存。今日は運用が変わった）

```ts
status: "active" | "closed" | "unverified"
```

| 値 | 意味 | 一覧 | 詳細ページ |
|---|---|---|---|
| `active` | 通常掲載 | 出る | 通常表示 |
| `closed` | 閉鎖・利用禁止が**確認できた** | 出ない | 赤い警告 |
| `unverified` | 営業状況が**確認できていない** | 出ない | 黄色い警告 |
| **`suspended`** | **再開予定のある休業** | 出ない | **青い告知** |

**今日変わった運用:** これまで「怪しいもの」は `closed` に寄せがちだったが、
`closed` は「閉鎖を確認した」という**積極的な主張**なので、確認できていないものに使ってはいけない。
`ito-marine-town-camp` は「実在が確認できない」なので `unverified` にした。

**そして「そもそも存在しなかったもの」には、どちらも使わない。レコードごと削除する。**
存在しなかったものに閉鎖の記録は要らないため（§4・§9参照）。

**`suspended` を後から足した理由。** `hayakawa-camp`（早川町オートキャンプ場）が
**災害復旧のため数ヵ年の休業**に入っていた。施設は実在し、名前も住所も合っていて、再開の予定もある。
`closed`（もう行ってはいけない）の赤い警告を出すのは事実と違うし、
`unverified`（確認できていない）でもない。**確認した結果が「今は行けないが将来復活する」**なので、
既存の3値では表せなかった。

```ts
status: "active" | "closed" | "unverified" | "suspended";
/** suspended のときの休業理由と再開見込み。出典URLを含めて書く */
suspendedNote?: string;
```

`validate-data.js` は **`suspended` なのに `suspendedNote` が空ならエラー**、出典URLが無ければ警告にしている。
「今は行けないが将来復活する」は積極的な主張なので、根拠なしに書かせない。

### 2-2. `restrictions` — 毎年繰り返す期間限定の制限

```ts
restrictions?: {
  type: 'bonfire' | 'camping' | 'access';
  from: string;   // "07-03" 形式の MM-DD。年は持たない
  to: string;     // "08-31"。from より小さければ年またぎ
  reason: string; // 利用者が読む文面
  source: string; // 条例名や資料名＋URL
}[]
```

**なぜ年を持たないか。** 海水浴場の開設期間も冬期通行止も毎年繰り返すので、
年を持たせると毎年データを書き換えることになる。MM-DD なら期間の定義は1回で済む。

**なぜ `from > to` を年またぎとするか。** 冬期閉鎖（12-10〜04-25）を表現するため。
判定は `md >= from || md <= to` になる。境界日と 12-31 / 01-01 のテストが
`scripts/test-restrictions.js` に入っている（**消さないこと**）。

**判定を閲覧時に行う理由。** 静的サイトなのでビルド時に「今は制限中」と焼き込むと、
翌日には嘘になる。だから静的HTMLは常に「期間制限あり・要確認」を出し、
`public/restrictions.js` が閲覧者のローカル日付で書き換える。

**フェイルセーフは要確認側。** JSが動かなければ「要確認」のまま残る。
ただし**期間・理由・出典はサーバ側で静的に出している。**
JSが落ちて消えていいのはラベルであって、中身ではない。

現在の設定: `wadanagahama-kaigan`（bonfire 07-03〜08-31）、`kofu-shinrinyoku-hiroba`（access 12-10〜04-25）。

**運用上の注意:** 和田長浜の開設期間は年により数日前後する。
`validate-data.js` に「`restrictions` を持つ施設の `lastVerified` が365日以上前なら警告」を入れてあるので、
**2027-08-07 以降のビルドで自動的に気づける。**

### 2-3. `eligibility` — 利用できる人の制限

```ts
eligibility?: {
  type: 'exclusive' | 'discount' | 'priority' | 'membership';
  label: string;
  note?: string;
  source: string;
}
```

**`type` は §9 の調査で4種類に増えたので後から足した。**
「誰が使えるか」は型によって利用者への意味がまるで違うので、表示の文言と色を型ごとに変えている。

| type | 意味 | 表示の見出し | 色 | 該当 |
|---|---|---|---|---|
| `exclusive` | **市外は使えない** | 利用できる人が限られています | 赤 | `kofu-shinrinyoku-hiroba`（甲府市民限定） |
| `discount` | 使えるが市外は割高 | 市外からの利用は割高になります | 黄 | `otome-forest-camp`（市民800円／市外2,000円）／`doshi-mori-cottage`（18歳以下の横浜市民を含むと割引） |
| `priority` | 居住者の申込が先に始まる | 地元の方の申込が先に始まります | 黄 | `hinata-camp`（市内は4月初旬、その他は4月下旬から） |
| `membership` | **会員登録が要る** | 会員登録が必要です | 赤 | `bushcraft-shonan` |

**排他型と会員制を赤にしたのは、「行っても使えない」可能性がある点で他の2つと質が違うから。**
料金差型と申込先行型は「使えるが不利」なので黄にしている。

**`discount` の場合、`priceMin` には市外料金を入れる。** このサイトの読者は市外から来る人が大半のため。

**`restrictions` と分けた理由。** 日付に依存しないので、JSを使わずビルド時に静的出力できる。
`restrictions.js` が失敗しても市民限定の表示は必ず残る。
首都圏在住のソロキャンパーにとって「市民限定」は行けるか行けないかを決める情報なので、
JSに依存させるべきではないと判断した。

### 2-4. `priceVerified` — 料金を一次情報で確認したか

```ts
priceVerified?: boolean   // 未設定・false = 未確認
```

**判定基準は `priceNote`（内訳）を書けたかどうか。** §1-4 の理由による。
現在 **153件 true / 24件 未設定**（当初は126/76。§9 の調査で76件を潰した結果）。

**この判定基準は指標として機能した。** `priceNote` を持たない76件を全件調べ直したところ、
**3分の1が実在しない施設だった**（§9-1）。内訳を書けていない＝一次情報に当たっていない、という読みは正しかった。

未確認のとき起きること。

- 金額を表示せず「料金 要確認」（一覧カード・詳細ページ・metadata の description）
- **JSON-LD の `priceRange` を出さない**（構造化データは検索エンジンがそのまま拾うため）
- 価格順ソートで末尾にまとめる（**除外はしない**。一覧から38%が消えると事故に見える）
- soloScore の計算でだけコスパを中立値3として扱う

**`scores.value` は書き換えていない。** 料金を確認して `priceVerified` を立てれば、
元の値がそのまま復活する。データを壊さずに済ませたかったため。

### 2-5. `coordsVerified` と `coordsGsiChecked` の違い

**これは今日いちばん重要な変更。**

```ts
coordsVerified?: boolean    // 人が地図上で目視確認した
coordsGsiChecked?: boolean  // 国土地理院の逆ジオコーディングを通過した
```

以前は `coordsVerified` 1つに両方の意味が混ざっていた。その結果、
**海上・湖面を指している7件に `coordsVerified: true` が立ったまま残っていた。**
「確認済み」を理由に検証対象から外す運用にしていたら、永久に見つからなかった。

現在 `coordsVerified` 146件 / `coordsGsiChecked` 168件。両方立っているのが140件。

**`coordsGsiChecked` が通っても地点が正しいとは限らない。**
「返ってきた市区町村が `prefecture` と矛盾せず、海上・湖面でもない」ことしか意味しない。
同じ市内の別地点でも通る。だから `coordsVerified`（人の目視）の代わりにはならない。

`coordsGsiChecked` は `scripts/apply-gsi-flags.js` が `coord-report.json` から機械的に埋める。
**手で書かないこと。** `coordsVerified` には逆にスクリプトから触らない
（人の目視の記録を機械の判定で上書きしないため）。

### 2-6. `needsCoord` の2通りの使い方

```ts
needsCoord?: boolean
```

**1. 座標をまだ取得できていない** … `lat`/`lng` は 0 のまま残す（推測値で埋めない）。
`validate-data.js` は `lat===0 && lng===0` のとき本フラグを必須にする。
該当: `nekumasanso-auto`

**2. 入っている座標が誤りと分かっているが、差し替える値をまだ確定できていない**
… `lat`/`lng` は**誤った値のまま残す**。
該当: 現在なし（`gandahara-manazuru` と `motosu-lakeside` がこの用途だったが、同日中に目視で確定して外した。§8参照）

**なぜ 0 で潰さないか。** 0 にすると「まだ取得していない」と区別が付かなくなる。
「誤りだと分かっている」という情報のほうが価値が高い。
どちらも「正しい座標が確定していない」点は同じなので、フラグは共用でよいと判断した。

## 4. 削除した3件と、その理由

**「実在しなかったもの」に `closed` や `unverified` の記録を残す意味はない。**
閉鎖したわけでも、確認待ちなわけでもなく、最初から無かったので、レコードごと削除した。

### `makiba-kogen-camp`（まきば公園キャンプ場）

**まきば公園はキャンプ場ではなかった。** 県立八ヶ岳牧場の一部の公園で、
ポニーや羊とふれあう施設。営業9:00〜17:00、入場無料、冬季（11/10〜4/19）閉鎖。テント宿泊はできない。

決定打は住所だった。データの「北杜市高根町清里**3545-1**」は、
隣の記録 `kiyosato-oka`（清里丘の公園キャンプ場）の「北杜市高根町清里**3545-5**」と**枝番だけが違う**。
実在するまきば公園の住所は「北杜市大泉町西井出8240-1」で町名から別物。**隣の記録からの流用**と判断した。

「まきば公園キャンプ場」で検索しても山梨県の該当施設は1件も出ない（千葉県の別施設が出る）。

### `ginga-momiji-camp`（銀河もみじキャンプ場）

**長野県下伊那郡阿智村浪合1771-1の実在施設。** 掲載範囲（神奈川・静岡・山梨）外。

## 6. 今日の教訓

**ここが一番重要。** 同じ失敗を繰り返さないために書いている。

### 6-1. 「確認済みフラグ」が検証をすり抜けさせた — 2件

**事例1: `coordsVerified` が座標検証を止めていた。**
海上・湖面を指す7件、清里3件、丹沢湖1件——**全部に `coordsVerified: true` が立っていた。**
このフラグを「検証済みだから見なくてよい」の意味で使う運用にしていたら、
これらは永久に見つからなかった。`verify-coords-gsi.js` がフラグを無視して全件を回す作りだったから見つかった。

**事例2: `duplicate-check.js` が `coordsVerified !== true` だけを対象にしていた。**
そのせいで `nakatsugawa-camp` × `nakatsugawa-kasenjiki`（座標が完全一致・0m）と
`tanzawako-lodge` × `tanzawako-roadside-camp`（名称完全一致）が検出対象から外れていた。
縛りを外したら、同じデータで 10ペア → 133ペアになった。

**教訓: 検証ツールの対象条件に「確認済みフラグ」を入れてはいけない。**
フラグが誤って立っているケースこそ検出したいのに、そのフラグで対象から外れる構図になる。
今日 `coordsVerified` と `coordsGsiChecked` を分けたのはこのため。

### 6-2. 出典の形式だけでは信用度を決められない

「GoogleマップのURL内の値のみ採用する」という規則で作業していた。
本栖レークサイドで、**山梨県公式観光サイト**の `maps.google.com/maps?q=35.502570,138.682973` を見つけた。
形式としては規則を満たしている。県の公式サイトでもある。

しかし逆ジオにかけると **西湖**を指していた。住所（本栖大久保）と一致しない。
同サイトの検索結果URLにも同じ値が地図の初期表示位置として現れることから、
**座標を持たないスポットのフォールバック中心**だった。

同じサイトの同じ形式が、浩庵では正しく機能していた。

**教訓: 出典が公式か、形式が規則に合うかで信用度を決めない。**
**必ず逆ジオコーディングで住所と突き合わせる。** この手順がなければ1.5km先へ飛ばしていた。
手順として組み込んであるチェックが、実際に誤りを1件止めた。

### 6-3. 実データでシミュレーションしないと逆効果に気づけない

料金が未確認の76件について「コスパのスコアに根拠がない」問題を扱ったとき、
**最も筋が通って見えた案は「コスパを計算から外す（4軸で /6 にする）」だった。**
判定できないものに点を付けない、という意味で正しく見えた。

実データで試したら**逆効果**だった。

| 案 | 上位20件に入る未確認施設 |
|---|---|
| 現状維持 | 2件 |
| **コスパを計算から外す** | **10件** |
| コスパを中立値3にする | 1件 |

理由は分かってみれば単純で、分母から外すと**残り4軸の平均が暗黙に代入される**。
76件のコスパ平均は3.53で全体より低いので、**除外すると得をして上位に上がる**。
「根拠のない数字で順位を付けない」という意図と正反対の結果になっていた。

**教訓: スコアリングや並び順の変更は、必ず実データで前後比較してから決める。**
理屈が通っていることと、狙った効果が出ることは別。

### 6-4. 実在しない施設は「実在する何かの名前や住所を借りて」作られる

今日までに見つかった実在しない施設は3件。**3件とも、実在する何かから借用していた。**

| slug | 何から借りたか |
|---|---|
| `sanogawa-camp` | 佐野川河川公園という実在の公園（ただしキャンプ禁止） |
| `ito-marine-town-camp` | 道の駅伊東マリンタウンの住所と、その**キャンプ場紹介ページ** |
| `makiba-kogen-camp` | 実在するまきば公園の名前＋隣の記録の住所（枝番だけ変更） |

だから「施設名で検索すると何かがヒットする」ことは実在の証明にならない。
**確かめるべきは「その名前でキャンプの予約・料金の情報が出てくるか」**。
道の駅伊東マリンタウンは実在するが、そこにキャンプ場は無かった。

**教訓: 実在確認は「名前がヒットするか」ではなく「予約・料金が出てくるか」で行う。**
なっぷ・じゃらん・公式のどれにも予約情報が無いなら、その施設は疑ってよい。

### 6-5. おまけ — デプロイ確認はキャッシュを疑う

Cloudflare のエッジキャッシュ（`CF-Cache-Status: HIT`）で、デプロイ直後の確認が
**2回とも旧内容を返した。** 一度は「デプロイが効いていない」と誤認しかけた。

```bash
curl -s -D h.txt "https://soro-camp.shun622shun39.workers.dev/about?bust=$(date +%s%N)" -o out.html
grep -i "^cf-cache-status" h.txt   # MISS を引くまで繰り返す
```

**デプロイ後の確認は、クエリ文字列でキャッシュを外し、`CF-Cache-Status` を必ず見ること。**

### 6-6. `needsVerify` は精度が高いが、網羅性が低い

§9 の調査で `needsVerify: true` が立っていたのは対象56件中**5件だけ**。
そのうち**4件が GHOST** だった（`kawanehon-camp` `nishiizu-seto` `nishiizu-dogashima-camp` `minobe-camp`）。
**フラグが立っていれば疑って正しい。**

問題は逆方向で、**GHOST 25件のうちフラグが立っていたのは4件（16%）だけ**だった。
残る21件は `needsVerify` なしで `status: 'active'` のまま、何の印もなく掲載されていた。

**教訓: `needsVerify` は「怪しいものを絞る」には使えるが、「フラグが無いから大丈夫」とは言えない。**
検証対象を選ぶときにフラグで絞り込むと、8割を見逃す。§6-1 と同じ構図がここにもある。

### 6-7. 「自治体の一覧に無い＝存在しない」は成り立たない

§9 の調査では、自治体・観光協会の施設一覧との照合が GHOST 判定の主力になった。
道志村32件・相模原市24件・山北町13件・富士宮市15件・西伊豆町6件・川根本町5件・静岡市5件・津久井地域7件。
1件ずつ検索するより速く、**「実在する施設の全体像」が分かるので借用元の特定にも使えた**。

ただし**一覧照合だけでは確定できない。反例が2件あった。**

- `sessokyo-camp`（接岨YANBY OUTDOOR FIELD）… **2023年開業**で川根本町の一覧が追いついていない。
  だが川根本町観光協会に施設ページがあり、**町のふるさと納税返礼品**にもなっていた
- `doshi-mori-cottage`（道志森のコテージ）… 村役場の32件に無いが、**村観光協会のサイト**に
  専用ページがあり空き状況まで出ていた

**教訓: 一覧照合は「候補の絞り込み」まで。確定には観光協会・ふるさと納税・予約サイトまで見る。**
新しい施設ほど自治体の一覧が遅れる。

### 6-8. キャンプ場が多いエリアほど、実在しない施設が紛れている

§9 の GHOST 25件のエリア分布。

| 県 | GHOST | 対象 | 率 |
|---|---|---|---|
| **神奈川** | **11件** | 26件 | **42%** |
| 山梨 | 8件 | 28件 | 29% |
| 静岡 | 6件 | 22件 | 27% |

市町村別では 相模原市4件・道志村4件・山北町2件・西伊豆町2件。

**この4つはいずれも本物の施設が密集しているエリア**（道志村は村公式に32件、相模原市は観光協会に24件、
山北町は町公式に13件）。**本物が多いほど、それらしい名前を1つ足しても気づかれにくい。**

**教訓: 「掲載数が多いから充実している」と読んではいけない。**
むしろ密集エリアこそ1件ずつ実在を確かめる価値がある。

### 6-9. `priceNote` の有無が「一次情報に当たったか」の指標になった

§1-4 で見つけた「`priceNote` を持たない76件と、住所が空の76件が完全に同一集合」という事実から、
**内訳を書けていない＝調べていない**と判断して76件を選んだ。

結果は VERIFIED 27 / PARTIAL 24 / **GHOST 25**。
**選び方が当たっていたことになる。** 料金を実際に調べた人は「入場料◯円＋サイト料◯円」の内訳を必ず書けるので、
値だけあって内訳が無いのは「調べずに置かれた値」のサインだった。

さらに、料金が**正しかったのは3件だけ**（`toyanosawa` / `camp-bean-izu` / `ecopa-inagako`）。
残り24件は最大 **+5,300円**（`suigennnomori`）から **−1,700円**（`oishii-camp`）までずれていた。

**教訓: データの正しさを直接測れないときは、「正しく調べた人なら必ず書けるはずの副次情報」を指標にする。**
`priceNote`（料金の内訳）はその役を果たした。同じ考えで使えそうなのは
`officialUrl`・`tel`・`address` の番地、`bonfireNote` の具体性あたり。
### 6-10. フィールドだけ直して soloComment を放置すると矛盾が残る

`numazu-shimin-no-mori` は `reservationNote` を「1週間前 → 3日前」に直したのに、
**soloComment の「1週間前までの予約を忘れずに」を据え置いていた。**
利用者が読むのは本文のほうなので、フィールドだけ正しくても意味がない。

同じことが `naminokomura`（area を小田原市に直したが本文は「湯河原の海岸沿い」）と
`tsuchimura`（設備の調査結果と本文が矛盾）でも起きていた。

**教訓: データを修正したら、必ず `soloComment` も読み直す。**
とくに**料金・予約・営業期間・地名**を変えたときは本文に同じ内容が書かれていないか確認する。

機械的に洗い出すなら、変更したフィールドの値を soloComment に対して突き合わせる。
今回は「N日前／N週間前」「N円」「通年」「地名」の4パターンで52件を検査し、3件を見つけた。
`scripts/apply-comment-consistency.js` に実際の検査観点が残してある。

### 6-11. `verify-coords-gsi.js` は `prefecture` の誤りを検出できない

`fujigane-kogen` は **prefecture が「静岡」（正しくは山梨）**で、座標も静岡県富士宮市を指していた。
`verify-coords-gsi.js` は「逆ジオの都道府県が `prefecture` と一致するか」しか見ないので、
**誤った県と誤った座標が一致してしまい OK と判定していた。**

`PREF_MISMATCH` は「県は正しく座標が間違っている」ケースしか捕まえられない。
**県の値そのものが間違っていると、この検査は無力になる。**

**教訓: 検査は「2つの値が一致するか」で組むと、両方同時に間違っているケースを見逃す。**
第3の情報と突き合わせる必要がある。この件では `address` の大字（富士ヶ嶺）と
逆ジオの `lv01Nm`（麓）が食い違っていたので、**住所の大字を突き合わせれば検出できた。**
§7 のタスクに実装を挙げてある。

### 6-12. `tel` が施設直通でなく予約窓口の番号のことがある

`duplicate-check.js` に電話番号一致の判定を足したところ、2組が引っかかった。
どちらも重複ではなく、**共通の予約窓口番号**だった。

| 番号 | 実態 | 該当 |
|---|---|---|
| 0555-30-4580 | PICA の予約センター | `pica-fuji-greenpa` / `pica-sagamiko` |
| 0547-59-2746 | 川根本町まちづくり観光協会 | `ikenoya-family` / `yagi-camp` |

**利用者が電話しても施設に直接つながらない。** 予約は取れるが、現地の状況（天気・混雑・道路）を
聞きたいときには役に立たない。**同じ番号を複数施設が持っていたら窓口番号を疑う。**

なお `hikenkayama`（火剣山キャンプ場）の `tel` も菊川市役所商工観光課（0537-35-0936）で、
これは調査時点で分かっていて意図的に入れたもの。窓口番号だと分かる形にするか、
施設直通と区別できるフィールドを持たせるかは検討課題（§7 のタスク）。

## 7. 残タスク（優先順）

**§9 の調査で、以前ここにあった4項目（76件の料金確認・76件の住所埋め・重点候補27件の実在確認・
`nakatsugawa-camp` の二重登録判定）は完了した。**残りを振り直したもの。

### 優先度 高

**1. 料金が取れなかった24件を潰す**
`priceVerified` が立っていない24件。詳細は `scripts/batch76-check.md` の PARTIAL 各項に
「何が取れなかったか」を1件ずつ書いてある。**実在と住所は確認済みなので、残るは料金だけ。**

取れなかった理由には型がある。

- **公式サイトに料金表がない**（`tiny-camp-village` `bushcraft-shonan` `folkwood-yatsugatake` ほか）
  → 予約サイトの日付指定ページか、電話
- **予約システム経由でないと金額が出ない**（`recamp-fuji-speedway` `shimobe-yurucamp-sato`）
  → なっぷの日付を指定して確認

**2. 住所が確定できなかった5件**
`pica-sagamiko`（番地）／`doshigawa-kanko-noen`（住所ごと）／`naminokomura`（番地）／

**`flora-campsite` は注意。** 検索で出る「北杜市高根町村山北割3261」は

**3. 道志川流域4件の座標**
PREF_MISMATCH 6件のうち `tsubakiso-auto` / `sankoso-auto` / `doshi-keikoku` / `woodsman-camp`。
4件とも道志村（山梨）の住所を持つのに、座標が県境の神奈川県側（相模原市緑区青根・牧野）に落ちている。

神奈川の住所を持ちGSIも整合しているので、一帯が全部おかしいわけではない。
県境が谷筋を走っているため、数百mのずれでも県が変わる。1件ずつ精度よく取り直す必要がある。

### 優先度 中

**4. `duplicate-check.js` の判定基準を締める**
全件総当たりにした結果、10ペア → 133ペアになった。**増えた123件の大半は誤検出。**
「富士」「朝霧」「山中湖」「PICA」などの地名・ブランド名の共通部分が3文字以上あれば拾ってしまう。

**縛りを外したこと自体は正しい。** §9 で削除した GHOST のうち複数を、このツールが先に指摘していた
（`nakatsugawa-camp` × `nakatsugawa-kasenjiki` 0.00km、`mountkan-kannogawa` × `nishitanzawa-mountbridge` 0.69km、

キャンピング／ヴィレッジ／village／camp／フィールド／サイト／リゾート／オート／ファミリー／パーク／河川敷 など。
「相模湖キャンピングヴィレッジ」→ `相模湖` のように**固有名だけが残る**。

**② 共通部分は「4文字以上かつ地名でない」に限定**
施設の `area`・`prefecture`・`address` に含まれる文字列を除外した。
「富士」「朝霧」「山中湖」は同じエリアの別施設なら当然一致するので根拠にならない。

**③ 強い根拠を2つ追加**
- **住所の番地一致** … 町名も一致なら「完全一致」。町名違いは20km以内のときだけ
  （「2745」「40-1」が100km離れて偶然一致した例が出たため距離条件を付けた）
- **電話番号の一致** … 今回の決め手になった条件

**新たに出た本物の重複は §10-4 の1組だけ。** ただし電話一致で2組が出て、
**どちらも重複ではなく「共通の予約窓口番号」**だった。

| ペア | 距離 | 実態 |
|---|---|---|
| `pica-fuji-greenpa` × `pica-sagamiko` | 51.8km | 0555-30-4580 は **PICA の予約センター番号** |
| `ikenoya-family` × `yagi-camp` | 2.7km | 0547-59-2746 は **川根本町まちづくり観光協会** |

### 10-6. フッターの最終確認日を動的にした

固定文字列「2026-05-26」が入っていて、データを更新しても直し忘れていた。
`lib/camp.ts` に `latestVerifiedDate()` を追加し、`lastVerified` の最大値を返すようにした。
プレースホルダ `2025-01-01` は除外している（現在0件だが、将来また混入したとき日付が過去に引き戻されないため）。

`soloScore` を JSON から外して計算に統一したのと同じ理由。**派生値は持たせない。**
