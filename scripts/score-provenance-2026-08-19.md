# 既存147件のスコアは、どういう根拠で付いているのか（調査・2026-08-19）

**読み取り専用の調査。**`data/campgrounds.json` には触っていない。

---

## 0. 結論を先に

| 問い | 答え |
|---|---|
| **機械で出しているのか / 人か / Claude か** | **一括投入時に Claude が付けた値**が大半。機械のルールでも、人のレビューでもない |
| **根拠がどこかに書かれているか** | **レコード単位の根拠はどこにも無い。**`scoreNote` に相当するフィールドが存在しない |
| **軸ごとの基準はあるか** | **ある。しかも公開されている。**`app/about/page.tsx` の `AXES` に 1〜5 の定義が全軸ぶん書いてある |
| **3に寄っているか** | **寄っていない。**静けさ・絶景は最頻値が **4**。全軸3は 192件中 **4件**だけで、それは千葉の `unverified` 4件（＝未評価の置き値） |

**★ ただし、引き継ぎdoc 自身が「根拠が追えない」と書いている**（優先度低 §14）:

> **14. スコアの再採点**
> 現在のスコアは一括投入時のものが多く、**根拠が追えない。**
> **コスパ軸は特に見直す価値がある。**

つまり「基準は文書化されているが、**個々の値がその基準に沿って付いた証拠は残っていない**」という状態。

## 1. 出どころ — 一括投入時に、レコードと一緒に書かれた

`git log -S'"quietness"' -- data/campgrounds.json` で追うと、
スコアは**バッチ投入のたびに新規レコードと同時に入っている**。最初の `118d1bc initial` まで遡る。

```
d0e4c78 add the five Yamanashi east sites that survived the precheck
3f878e8 道志村から3件を追加（181→184件）
…
65943ee feat: add batch7 30 camps (150->180)
b817f37 feat: add batch6 36 camps (114->150)
07a1989 data: batch5 新規14件追加（重複6件スキップ）合計114件
…
118d1bc initial: soro-camp solo camping guide
```

`scripts/batch7.json` の1件目を見ると、**投入用の JSON に最初から scores が書かれている**:

```json
{
  "id": "hayato-hakone",
  "name": "HAYATO 箱根キャンプ場",
  "scores": { "quietness": 5, "scenery": 4, "value": 3, "access": 3, "facility": 3 },
  "features": { … },
  "soloComment": "箱根の静かな林間、ソロ専用区画あり。…"
}
```

`apply-batch7-2026-05.js` は**この JSON をそのまま追記するだけ**で、スコアを計算していない。
**つまりスコアはバッチ JSON を作った時点で決まっている。**
バッチ JSON を生成した過程はリポジトリに残っていない（生成スクリプトが無い）。

**→ 実態は「Claude が施設情報を見て付けた値」。**機械のルールではないし、人が1件ずつレビューした記録も無い。

## 2. 基準は存在する。しかも公開されている

`app/about/page.tsx` の `AXES` 定数。**サイトの `/about` に出ている。**

| 軸 | 重み | 定義 | 1〜5 の目安 |
|---|---|---|---|
| **静けさ** `quietness` | **×2** | 夜の静かさ、隣サイトとの距離、団体・ファミリー層の多さ | 5 区画が離れ夜はほぼ無音／4 基本的に静か／3 平均的・週末は賑わう／2 団体が多く話し声が届く／1 常時賑やか |
| **絶景** `scenery` | **×2** | サイトから見える景色。富士山・湖・渓谷・海など | 5 目的地になりうる景観／4 印象に残る眺め／3 平均的な林間・河原／2 特筆すべきものなし／1 眺望なし |
| **コスパ** `value` | ×1 | 料金に対する満足度。ソロ料金の設定、設備に見合う価格か | 5 無料か相場よりかなり安い／4 相場より安い・ソロ割／3 相場どおり／2 やや高い／1 割高 |
| **アクセス** `access` | ×1 | 主要道路からの距離、道の走りやすさ、買い出しのしやすさ | 5 幹線道路沿い・買い出し容易／4 迷わず行ける・スーパー近い／3 平均的／2 山道が長い／1 悪路・長距離 |
| **設備** `facility` | ×1 | トイレの清潔さ・様式、シャワーや風呂、水場、売店 | 5 ウォシュレット・風呂・売店／4 清潔なトイレとシャワー／3 一通り／2 最低限・和式のみ／1 トイレ・水場なし |

```
soloScore = (静けさ×2 + 絶景×2 + コスパ + アクセス + 設備) ÷ 7
```

**★ この基準は「計算式」ではなく「言葉の目安」。**
「平均的」「印象に残る」は、**データ項目に対応していない。**
だから同じ基準を機械で再現することはできない。**人（または Claude）が読んで当てる前提の基準。**

`/about` にはこう書いてある — **「スコアは公開情報にもとづく当サイトの評価であり、実測値ではありません。」**

## 3. 分布 — 3に寄っていない

`status: 'active'` の **147件**:

| 軸 | 1 | 2 | 3 | 4 | 5 | 最頻 |
|---|---:|---:|---:|---:|---:|---|
| 静けさ | 0 | 6 | 32 | **80** | 29 | **4** |
| 絶景 | 0 | 1 | 41 | **69** | 36 | **4** |
| コスパ | 0 | 11 | 52 | **55** | 29 | **4**（3とほぼ拮抗） |
| アクセス | 2 | 20 | **60** | **60** | 5 | **3/4** |
| 設備 | 5 | 8 | **61** | 59 | 14 | **3** |

- **5軸の組み合わせは 109 種類 / 192件。**judgement が1件ずつ振られている形
- **全軸3のレコードは 192件中 4件だけ**で、その4件は**千葉の `unverified`**
  （`orange-mura-auto` / `otaki-kenminnomori` / `otaki-sabo` / `kisarazu-camp-organic`）＝
  `lib/types.ts` が言う**「未評価の置き値」**そのもの

**⚠ ただし分布に偏りはある。**静けさ・絶景は **4以上が 109/147・105/147**。
**「ソロ向けに選んだ施設だから高い」のか「甘めに付いている」のかは、この分布だけでは分からない。**

## 4. `scoresVerified` は 147件すべてで**未指定**

`lib/types.ts` の定義:

> `scores`（5軸）を**人が評価したか。**
> **`false` は「評価していない」であって「低い」ではない。**
> 料金だけ一次情報で取れて設備を見ていない段階のレコードは、全軸に 3 を置くが
> それは中庸の評価ではなく**未評価の置き値**。
> **未指定は「不明」。**

実測:

| 値 | 全192件 | active 147件 |
|---|---:|---:|
| `true` | **0** | **0** |
| `false` | 4（千葉の unverified） | 0 |
| 未指定 | 188 | **147** |

**→ 「人が評価した」と記録されているレコードは1件も無い。**
147件は全部「不明」の状態でサイトに出ている。

## 5. 機械で採点した前例はある。ただし**14件だけ**

`scripts/apply-wild-rescore-2026-08.js`（旧 `rescore-wild.js`）。
記録は `scripts/rescore-notes.md`。

- **対象**: `type: "wild"` の**14件だけ**（野営地）。147件全体ではない
- **材料**: `features`（notes 含む）/ `cautions` / 料金 / 営業期間 / 予約要否 **のみ**。
  **`name` や `soloComment` からの推測は使わない**（施設名から景観を想像するのは推測、と明記）
- **方式**: **10人のペルソナ**（野営歴20年・ソロ初心者・バイク勢・冬キャン勢・徒歩勢・
  写真勢・節約勢・直火勢・安全重視・リピーター）が**根拠のある軸だけ採点し、無ければ棄権**
- **採点者が5人未満（`MIN_RATERS = 5`）の軸は「根拠不足」として既存値を据え置く**
- 10人の平均を四捨五入して採用

**★ ここが今日の話と直結する。**`rescore-notes.md` の「根拠不足で据え置いた軸」:

| 軸 | 据え置き | 備考 |
|---|---|---|
| 静けさ | 0 / 14 | — |
| **絶景** | **14 / 14** | **features / cautions に景観を判断できる情報がないため、全件で採点不能** |
| コスパ | 0 / 14 | — |
| アクセス | 0 / 14 | — |
| 設備 | 0 / 14 | — |

**既存のやり方でも絶景は採点できていない。**今日 STEP C で出した結論と同じ。
違いは、**あちらは「採点不能なら既存値を据え置く」**という逃げ道を持っていたこと
——**そしてその既存値は、一括投入時に Claude が付けた値。**

## 6. ★ もう1つ、今日の設計に直接効く既知の実測（引き継ぎ §6-3）

料金未確認76件の「コスパに根拠がない」問題を扱ったとき、
**「コスパを計算から外す（4軸で /6）」が最も筋が通って見えた**が、実データで逆効果だった:

| 案 | 上位20件に入る**未確認**施設 |
|---|---|
| 現状維持 | 2件 |
| **コスパを分母から外す** | **10件** |
| コスパを中立値3にする | 1件 |

理由は「分母から外すと**残り4軸の平均が暗黙に代入される**」から。
76件のコスパ平均は 3.53 で全体より低いので、**外すと得をして上位に上がった。**

> **教訓: スコアリングや並び順の変更は、必ず実データで前後比較してから決める。**

**→ STEP C で提案していた「欠測は `null`。平均の分母に入れない」は、この罠と同じ形。**
採るなら**実データで前後比較してから**。理屈が通っていることと、狙った効果が出ることは別。

（現行実装は逃げ道を1つ持っている: `lib/camp.ts` は
**`priceVerified` が立っていない施設だけ、`soloScore` の計算で `scores.value` を中立値3に差し替える**。
`scores.value` 自体は書き換えず、料金を確認すれば元の値が復活する。）

## 7. 46件に同じやり方を当てるとき、決めないといけないこと

**既存147件と同じやり方＝「基準（`/about` の言葉の目安）を読んで、施設情報から Claude が当てる」。**
それに揃えるなら、次は判断が要る:

1. **材料をどこまでにするか。**
   既存のバッチ投入は材料が記録されていない。`rescore-wild` は
   **features / cautions / 料金 / 営業期間 / 予約要否に限定し、名前と soloComment を除外**した。
   **後者のほうが厳しく、今日の絶対ルール（推定禁止）に近い。**
   46件は STEP A で `siteInfo` / `accessInfo` / `ruleInfo` / `chargeInfo` の原文が取れているので、
   **`rescore-wild` より材料は多い。**
2. **絶景をどうするか。**既存も採点できていない。
   一括投入時の値は**根拠が追えない**ので、「既存に揃える」＝「根拠なしで付ける」になってしまう。
   **46件は新規なので据え置く既存値が無い。**ここだけは新しい判断が要る。
3. **`scoresVerified` を今度こそ立てるか。**
   147件は全部「不明」。46件で `true` を立て始めるなら、**何をもって true とするか**の定義が要る。
