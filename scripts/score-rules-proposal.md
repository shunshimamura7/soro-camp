## 1. いま手元にあるデータ（STEP A の実測）

なっぷ詳細ページから取れた項目。**取得元は2か所** — JSON-LD（`@type: Campground`）と
RSC ペイロードの `campsite` オブジェクト。

### 取れるもの

| 項目 | 中身 | 型 |
|---|---|---|
| `chargeInfo` | 料金表 | **HTML 原文**（施設が書いたまま） |
| `siteInfo` | 場内の設備の説明 | HTML 原文 |
| `accessInfo` | アクセスの説明 | HTML 原文 |
| `parkingInfo` | 駐車場 | HTML 原文 |
| `ruleInfo` | 場内ルール | HTML 原文 |
| `rentalInfo` | レンタル品 | HTML 原文 |
| `seasonInfo` / `holidayInfo` | 営業期間 / 定休日 | HTML 原文 |
| `checkinInfo` / `checkoutInfo` | 「13:00～17:00」 | 文字列 |
| `priceRange` | 「3300-52800」 | 施設全体の幅 |
| `ratingValue` / `ratingCount` | 口コミ平均 / 件数 | 数値 |
| `favoriteNum` / `alreadyWentNum` | お気に入り数 / 行った数 | 数値 |
| `telephone` / `hpUrl` | 電話 / 施設公式URL | 文字列（**`hpUrl` は空のことがある**） |
| `masterList.*` | activities / nearFacilities / locationEnvironment / ground / equipment / facilities ほか | **数値コードの配列** |

### ★ 取れないもの（**推定で埋めない**）

| 欲しかった | 実際 |
|---|---|
| **区画数・サイト総数** | **構造化されていない。**「1区画あたり」のように単価の説明として出るだけで、総数を書いている施設は少ない |
| **標高** | **キーが無い。**なっぷは持っていない |
| **`masterList` の意味** | **コード→ラベルの辞書がページ内に無い。**`equipment:[43,48,50,…]` の 43 が何かは分からない |
| **眺望・景観** | 写真はあるが**画像は解析しない。**文章で景観に触れているかどうかしか分からない |

**`masterList` について。**コードの意味が分からない以上、**「コードが何個付いているか」を設備の豊かさとして使わない。**
個数は「その施設に何個のタグが付いたか」であって、タグの中身が分からなければ意味が決まらない。
**使うなら先に辞書を取る**（なっぷの検索絞り込みページにコードとラベルの対応がある可能性が高い。未調査）。

## 2. 軸ごとの提案

各軸は **0〜5 の整数**、または **`null`（算出不能）**。

### 2-1. 設備 — **これがいちばん素直に出せる**

**データ**: `siteInfo` の原文（＋ `rentalInfo` / `cardFlg`）。

**式**: 施設自身が書いている設備語の**有無**を数える。「書いてある」は事実で、推定ではない。

```
設備点 = 以下のうち原文に出現するものの数（各1点、上限5）
  ① トイレ           /トイレ/
  ② 炊事場・炊事棟    /炊事|流し|シンク/
  ③ シャワーまたは風呂 /シャワー|風呂|浴場|温泉/
  ④ 売店または自販機   /売店|購買|自販機|自動販売機/
  ⑤ AC電源           /電源|AC ?電源|コンセント/
スコア = min(5, 設備点)
```

**閾値**: 生の点数をそのままスコアにする（0〜5）。変換しない。

**欠測**: `siteInfo` が空 → **`null`（算出不能）**。
**⚠ 0点と算出不能を混同しない。**「設備の説明を書いていない施設」と「設備が無い施設」は違う。

**限界（先に書いておく）**: これは**「施設が説明文に書いたかどうか」の指標**であって、設備の実在ではない。
説明が短い施設は低く出る。**指標名を「設備」と呼ぶなら、この限界を soloComment 側に書けない。**
正直な名前は「設備の記載充実度」。

---

### 2-2. コスパ — **STEP B が通った施設だけ出せる**

**データ**: STEP B で確定した**ソロ1名の総額**（`priceMin`）。**なっぷの `priceRange` は使わない**
（施設全体の幅で、コテージやヴィラを含むので solo の実額ではない）。

**式**: 千葉の**確定済みソロ総額の分布の中での位置**で決める。絶対額の閾値は置かない
（地域差・年次差でハードコードが腐る。§18-3）。

```
p = priceMin の百分位（確定済み母集団の中で安いほど小さい）
スコア = 5 - floor(p × 5)   … p<0.2 → 5 / 0.2-0.4 → 4 / 0.4-0.6 → 3 / 0.6-0.8 → 2 / 0.8以上 → 1
```

**★ 母集団を明記すること。**「千葉の確定済み N 件の中での相対位置」。
**N が小さいうちは順位が乱高下する。**N が二桁に乗るまでは、この軸は
**「暫定」ではなく「母集団 N 件基準」と書いて数字を添える。**

**欠測**: `priceVerified` が立っていない → **`null`。**
**⚠ なっぷの金額で代用しない。**代用した瞬間に priceVerified の意味が消える。

---

### 2-3. アクセス — **原文に距離か時間が書いてあるものだけ**

**データ**: `accessInfo` の原文。

**式**: 高速IC からの距離または所要時間を原文から読む。

```
IC からの所要時間 t（分）が原文にあれば
  t ≤ 10 → 5 / ≤ 20 → 4 / ≤ 30 → 3 / ≤ 45 → 2 / それ以上 → 1
距離 d（km）しか無ければ
  d ≤ 5 → 5 / ≤ 10 → 4 / ≤ 20 → 3 / ≤ 35 → 2 / それ以上 → 1
両方あれば時間を採る（**時間のほうが施設の主張として具体的**）
```

**欠測**: `accessInfo` が空、または IC からの距離・時間が書かれていない → **`null`。**
**⚠ 座標から計算しない。**「最寄りICまで直線距離○km」は**こちらが作った数字**で、
一次情報ではない（距離ベースの閾値を作らない、という今日の絶対ルールにも当たる）。

**限界**: 「公共交通で行けるか」は評価していない。ソロキャンプの文脈では
車前提でよいと思うが、**それは判断であって式ではない**ので、採るならここに1行書く。

### 2-4. 静か — **★ 大半が算出不能。式は書けるが母数がほとんど無い**

**使えないデータと、その理由:**

| 候補 | なぜ使えないか |
|---|---|
| 区画数（少ない＝静か） | **区画数が取れない**（§1）。取れる施設だけで出すと、書いている施設だけが評価される |
| 立地（林間・高原＝静か） | `locationEnvironment` は**コードで意味が不明。**`siteInfo` の「林間」は施設の宣伝文で、静けさの根拠にならない |
| 口コミ本文（「静かでした」） | **他人の印象。**しかも JSON-LD に載るのは2件だけ。標本として使えない |
| 周辺に道路・鉄道が無い | **座標からの推定。**やらない |

**唯一データとして立つもの**: `ruleInfo` に**消灯時間・静粛時間の明記があるか。**
これは施設が定めた規則で、事実。

```
ruleInfo に 消灯/静粛/クワイエットアワー の時刻指定がある → 4
ruleInfo に 騒音・音響機器・花火の禁止規定がある         → 3
ruleInfo はあるが静けさに関する規定が無い               → 2
ruleInfo が空                                        → null（算出不能）
```

**★ この式の限界は率直に重い。**測っているのは「**静かにさせる意思がある施設か**」であって、
「**静かな場所か**」ではない。**軸名を「静か」のままにするなら、この式は名前に対して嘘をつく。**
→ §6 の判断待ち。

---

### 2-5. 絶景 — **★ 算出不能。式を提案しない**

**眺望を判定できるデータが1つも無い。**

- 画像はあるが**解析しない**（この判断は変えないほうがいい）
- `locationEnvironment` は**コードで意味不明**
- `charmList` の caption は**施設の宣伝文**。「絶景」と書いてあるのは景色の証拠ではなく、書いた事実の証拠
- 地名・住所から「海沿いだから絶景」は**推定**。禁止

**強いて式を作るなら**「施設が景観に言及しているか」だが、
**それは絶景の指標ではなく宣伝文の指標。**名前を偽ることになるので**提案しない。**

→ **この軸は現状 `null` 固定。**埋める道は §6-案3 だけ。

## 3. 欠測の扱い（全軸共通）

```
score = { 静か: n|null, 絶景: n|null, コスパ: n|null, アクセス: n|null, 設備: n|null }
```

- **`null` を 3 に置き換えない。平均を取るときも分母に入れない**
- レコードには**「どの軸がなぜ算出不能か」を1行で持つ**（`scoreNote`）。
  「算出不能」だけでは次に何をすれば埋まるかが分からない（§21-4 と同じ理由）
- **表示側**: `null` の軸は「—」で出す。**0 と描き分ける**

## 6. ★ 判断してほしいこと — 3案

**基準（実在確認 + priceVerified + 5軸に根拠）は下げない前提で、どれを採るか。**

### 案1. 5軸そのまま・厳格運用 → **active は 0 件のまま**

絶景が埋まらないので誰も昇格しない。**基準はいちばんきれいだが、サイトに何も出ない。**
「まだ出さない」を選ぶならこれ。

### 案2. 軸を**データが支える名前に付け替える**（推奨）

出せないものを出せるふりにしない代わりに、**測れているものを正しい名前で出す。**

| いまの軸 | 案2での名前 | 根拠 |
|---|---|---|
| 設備 | **設備の記載充実度** | `siteInfo` の設備語（事実） |
| コスパ | **コスパ（千葉N件内の相対）** | 確定 `priceMin` の百分位 |
| アクセス | **IC からの近さ** | `accessInfo` の原文 |
| 静か | **静粛ルールの明確さ** | `ruleInfo` の規定（事実） |
| 絶景 | **廃止 or 保留（`null` 固定）** | データが無い |

**利点**: 全部が原文の事実に紐づく。嘘をつかない。
**代償**: 「絶景」がサイトから消える（または常に「—」）。5軸が4軸になる。

### 案3. 絶景・静かを**別工程で人が埋める**

一次情報（施設公式・自治体公式）を人が読んで、**根拠URL付きで**手入力する。
**暫定値3ではなく、根拠のある実値。**
46件なら現実的な量だが、**今日の自動処理の範囲外。**
